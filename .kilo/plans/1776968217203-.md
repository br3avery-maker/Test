# Project Plan: Tap-to-Mine Android WebApp/Game with Blockchain Node on Google Drive

## Executive Summary
A Progressive Web App (PWA) game combining literal **tap-to-mine** mechanics—where physical screen-tapping data generates cryptographic hashes—with blockchain integration. Users host their own blockchain nodes using Google Drive as storage infrastructure, built on block-lattice architecture (Nano-style) for feeless, instant transactions.

## 1. System Architecture

### 1.1 Frontend (PWA)
- **Framework**: Vanilla JS with Vite (or React for complex state)
- **PWA Features**: Service worker, offline support, installable to home screen
- **Game Engine**: Canvas-based for tap mechanics, Phaser.js optional
- **Wallet Integration**: Web3Modal for multi-wallet support
- **Crypto API**: Web Crypto API for browser-based key management

### 1.2 Blockchain Layer
- **Choice**: Custom lightweight blockchain using literal tap entropy
- **Consensus**: Delegated Proof of Stake (DPoS) with tap-mined blocks
- **Node Implementation**: Lightweight JavaScript blockchain client
- **Storage**: Google Drive API for distributed node data persistence

### 1.3 Backend Services
- **Authentication**: Google OAuth 2.0 + Web3 wallet signatures
- **API Layer**: RESTful or GraphQL API for game state
- **Node Sync Service**: Background sync of blockchain state via Google Drive
- **Real-time Updates**: WebSocket for live game/chain updates

### 1.4 Data Storage
- **Primary**: Google Drive API (multipart uploads, resumable uploads)
- **Local**: IndexedDB for offline-first caching
- **Cache**: Service Worker Cache API for static assets
- **Blockchain State**: JSON files on Google Drive representing chain state

## 2. Blockchain Design

### 2.1 Block-Lattice Architecture
- Each user has their own blockchain (account-chain)
- Account control via private key (ED25519 or secp256k1)
- Asynchronous updates - no global consensus bottleneck
- Transaction = signed block containing state transition

### 2.2 Transaction Structure
```json
{
  "type": "state",
  "account": "<public_key>",
  "previous": "<previous_block_hash>",
  "representative": "<delegate_address>",
  "balance": "<current_balance>",
  "link": "<optional_link>",
  "signature": "<ed25519_signature>",
  "work": "<proof_of_work>",
  "tap_entropy": "<hash_of_tap_data>"
}
```

### 2.3 Literal Tap-to-Mine: Hashing Physical Input
- **Tap Data Capture**: Coordinates (x,y), timestamp, touch pressure, duration, inter-tap interval
- **Entropy Pool**: Aggregated tap data fed into SHA-256 hash generation
- **Hash Generation**: H(tap_data + previous_hash + nonce) → target_difficulty
- **Physical Randomness**: Human motor imprecision provides true entropy source
- **Difficulty Target**: Adjustable leading zeros required in hash output
- **Block Creation**: Valid hash with sufficient difficulty creates new block
- **Tap Signature**: Each tap cryptographically signed with user's private key
- **Validation**: Network verifies hash meets difficulty AND tap signature valid

### 2.4 Mining Mechanics
- **Dynamic Difficulty**: Adjusts based on network-wide hashrate (taps/second)
- **Block Rewards**: Fixed tokens per valid mined block (e.g., 100 tokens per hash)
- **Energy Efficiency**: No computational proof-of-work—uses human physical input
- **Fair Distribution**: Limited by physical tapping speed (anti-bot)
- **Rate Limiting**: Max taps per second to prevent automated scripts
- **Progressive Difficulty**: Increases with cumulative network power

### 2.5 Node Operations
- **Block Propagation**: Via Google Drive file updates
- **State Synchronization**: Periodic sync with chain state files
- **Conflict Resolution**: Last-write-wins with signature verification
- **Voting**: Delegated representatives confirm transactions
- **Tap Validation**: Verify tap hash meets difficulty target before confirming block

### 4.3 Tap-to-Mine Mechanics: Physical Input Processing
- **Tap Event Capture**: touchstart/touchend with full PointerEvent data
- **Data Points per Tap**:
  - Screen coordinates (x, y) normalized to device resolution
  - Touch pressure (0.0 to 1.0 from Force Touch/3D Touch)
  - Touch radius/contact area
  - Timestamp with microsecond precision (performance.now())
  - Duration (touch_end - touch_start)
  - Inter-tap interval (time since previous tap)
  - Multi-touch patterns (fingers count, spread distance)
- **Entropy Aggregation**: Accumulate tap data in rolling window (last N taps)
- **Hash Construction**:
  ```javascript
  const tapData = {
    coords: [x, y],
    pressure: force,
    duration: deltaTime,
    prevInterval: timeSinceLastTap,
    nonce: randomBytes(32),
    timestamp: performance.now()
  };
  const message = JSON.stringify(tapData) + previousBlockHash;
  const hash = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(message));
  const difficultyMet = hash.startsWith('0'.repeat(currentDifficulty));
  ```
- **Difficulty Target**: Current network difficulty (e.g., 4 leading zeros = 16^4 = 65,536 tries average)
- **Real-time Feedback**: Visual hash progress bar showing proximity to target
- **Streak Multipliers**: Consecutive successful hashes increase reward multiplier
- **Combo System**: Rapid successive taps within time window boost difficulty achievement
- **Physical Fatigue Modeling**: Slower tap rate expected over time, difficulty auto-adjusts

### 4.4 Anti-Cheating & Bot Protection
- **Human Verification**: Tap timing analysis—humans have 100-300ms variability, bots are more regular
- **Pattern Detection**: Machine learning to identify automated tap patterns vs natural human variation
- **Rate Limiting**: Maximum 10 taps/second per device (physical human limit)
- **Entropy Quality Checks**: Verify tap coordinate variance—true human taps have natural jitter
- **Device Fingerprinting**: Prevent multiple accounts from same device farming
- **Geographic Distribution**: Ensure taps come from claimed locations
- **Pressure Validation**: Verify pressure values are physically plausible for device
- **Acceleration Analysis**: Check tap velocity/acceleration matches human motor patterns

## 10. Scalability & Performance Optimization

### 10.1 Performance Strategies
- **Lazy Loading**: Load blockchain state on-demand, not all at once
- **Chunked Sync**: Sync only recent N blocks, archive older blocks
- **Compression**: Gzip/brotli for blockchain JSON files on Drive
- **CDN Caching**: Cache static assets via CloudFlare
- **IndexedDB**: Local-first architecture, sync to Drive in background
- **Delta Encoding**: Only transmit changed portions of chain state
- **Web Workers**: Offload crypto operations to background threads
- **WASM Acceleration**: Use WebAssembly for cryptographic primitives

### 10.2 Scaling Blockchain Operations
- **Sharding**: Partition blockchain by user groups/regions
- **Hierarchical Structure**: Local chains → Regional chains → Global chain
- **Batch Processing**: Combine multiple block confirmations
- **Optimistic Concurrency**: Assume valid, verify asynchronously
- **Eventual Consistency**: Accept temporary forks, resolve via voting

### 10.3 Google Drive Optimization
- **File Structure**: Shard across multiple files to avoid size limits
- **Batch Requests**: Use batch API for multiple operations
- **Resumable Uploads**: For files >5MB
- **Quota Management**: Track usage, implement backoff
- **Cache Headers**: Max-age for frequently accessed files
- **Delta Sync**: Use changes API instead of full re-read

### 10.4 Database Optimization (IndexedDB)
- **Object Stores**: Separate stores for blocks, state, metadata
- **Indexes**: Create indexes on hash, account, timestamp
- **Pruning**: Remove old confirmed blocks locally
- **Compaction**: Periodic database cleanup

### 10.5 Network Optimization
- **Request Batching**: Combine API calls
- **Connection Pooling**: Reuse HTTP connections
- **Compression**: Accept-Encoding: gzip, deflate, br
- **Protocol Buffers**: Consider binary format instead of JSON

### 10.6 Game Performance
- **Canvas Optimization**: Minimize redraw regions
- **Animation Frames**: Use requestAnimationFrame
- **Memory Management**: Dispose unused objects
- **Asset Loading**: Preload and sprite sheets

### 10.7 Benchmarks & Targets
- Initial sync: <30 seconds for 1000 blocks
- Transaction confirmation: <3 seconds
- Tap response time: <100ms
- Hash computation: <50ms per attempt
- Page load (cached): <2 seconds
- Drive sync (background): <5 seconds per 100 blocks

### 10.8 Monitoring & Metrics
- **Performance Metrics**: FPS, load time, sync time, hash rate
- **Resource Usage**: Memory, CPU, network
- **Error Rates**: Failed syncs, API errors
- **User Metrics**: Engagement, retention
- **Hash Metrics**: Taps/second, success rate, difficulty

## 11. Risk Assessment

### Technical Risks
- **Google Drive Quota**: Limited API calls, implement aggressive caching
- **Web Crypto Limitations**: Not all algorithms available in-browser, use WASM fallback
- **Browser Support**: PWA features vary, progressive enhancement required
- **Blockchain Complexity**: High complexity, start with simplified model
- **Entropy Quality**: Human tapping may not provide sufficient randomness

### Business Risks
- **Ad Blockers**: Diversify revenue streams beyond ads
- **Wallet Adoption**: Simplify onboarding, abstract complexity
- **Regulatory**: Cryptocurrency regulations vary by jurisdiction
- **Competition**: Differentiate with unique gameplay
- **User Fatigue**: Physical tapping may become tedious

### Mitigation Strategies
- **Offline-First**: Core features work without internet
- **Multiple Revenue Streams**: Don't rely on single source
- **Compliance**: Legal review before launch
- **Unique Value Prop**: Focus on fun gameplay first, blockchain second
- **Auto-Mine Mode**: Optional automatic tapping for accessibility

### 14.2 CI/CD Pipeline
```yaml
# GitHub Actions Example
name: Deploy PWA
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-node@v3
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm run test:unit
      - run: npm run test:e2e

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-node@v3
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-artifact@v3
        with:
          name: dist
          path: dist/

  deploy:
    needs: build
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/download-artifact@v3
        with:
          name: dist
          path: dist/
      - uses: peaceiris/actions-gh-pages@v3
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./dist
```
